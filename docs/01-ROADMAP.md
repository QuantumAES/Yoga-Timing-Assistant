# Дорожная карта проекта «Yoga Timing Assistant»

**Дата:** 2026-07-26
**Базис:** `ТЗ.md` + `docs/00-ANALYSIS.md`
**Оценка:** 55–77 рабочих дней ≈ **11–15 недель** для 1 senior Android-разработчика
**Целевая дата MVP в Play (internal → production):** ~ноябрь 2026 при старте в августе

---

## 1. Стратегические принципы плана

### 1.1. Риск вперёд, красота потом

Главный риск проекта — **не вёрстка, а надёжность фонового исполнения** (R-1). Поэтому план намеренно нарушает привычный порядок «сначала UI, потом логика»:

> **Веха M2 (конец недели 4): вертикальный срез.**
> Захардкоженный профиль из 3 этапов честно отсчитывается на реальном устройстве при заблокированном экране, свёрнутом приложении и включённой оптимизации батареи. UI — три `Text` без стилей.

Если M2 не берётся на матрице устройств — весь проект пересматривается на неделе 4, а не на неделе 12. Это самая дешёвая точка для разворота.

### 1.2. Ядро таймера — чистый Kotlin без Android

`TimerEngine` выносится в отдельный JVM-модуль без единой ссылки на `android.*`. Следствия:
- тестируется виртуальным временем (`kotlinx-coroutines-test`) — 90-минутная сессия проверяется за миллисекунды;
- дрейф, границы этапов, ±30 с, переходы покрываются юнит-тестами, а не ручным сидением с секундомером;
- Android-специфика (WakeLock, Service, AlarmManager) — тонкий адаптер вокруг.

### 1.3. Порядок фаз соответствует убыванию риска

```
Риск ↓   Ядро таймера → Оповещения → Данные → Редакторы → Полировка
Стоимость исправления ↑
```

### Фаза 3 — Ядро таймера и фоновая работа · 8–12 дн ⚠️ КРИТИЧЕСКИЙ ПУТЬ

Самая рискованная и самая дорогая фаза. Не сокращать.

| Задача | Детали |
|---|---|
| `:timer-engine` (чистый JVM) | state machine IDLE→RUNNING→PAUSED→TRANSITION→FINISHED; отсчёт по `elapsedRealtime`; `next/prev/±30с`; FREE-этап (счёт вверх) |
| Юнит-тесты движка | виртуальное время: 90-мин сессия, дрейф, границы, все переходы, edge cases §8 ТЗ. **Покрытие ≥ 85%** |
| `TimerService` (FGS) | тип `specialUse` (P0-3), `START_STICKY`, partial WakeLock, notification с действиями Пауза/Далее/Стоп |
| Уведомление | обновление ≤ 1 Гц, корректная отмена, канал уведомлений |
| Watchdog-аларм | ровно один exact-аларм на ближайшее критичное событие (P0-2) |
| Персистентность сессии | по событиям, не по таймеру (P1-3); `bootId` + обе метки времени (P1-4) |
| Восстановление после kill | «Продолжить занятие?» если прошло < 5 мин |
| Детект ограничений | статус battery optimization / exact alarm / notifications → флаг для UI-баннера |
| Минимальный UI-заглушка | 3 `Text` + 3 кнопки, только для проверки |

**DoD / M2 — «Вертикальный срез»:**
- профиль из 3 этапов проходит целиком при заблокированном экране и свёрнутом приложении;
- управление из шторки работает;
- убийство процесса (`adb shell am kill`) → восстановление сессии;
- **проверено вручную на матрице устройств**, результат зафиксирован в `docs/04-DEVICE-MATRIX.md`;
- дрейф за 60 мин < 1 с (замер).

> Здесь принимается решение go/no-go по архитектуре. Если OEM-устройства не держат FGS — пересмотр (вплоть до отказа от полной фоновой работы в MVP и явного требования держать экран включённым).

**Состояние на 2026-07-28.** Код фазы готов и проверен автотестами:
`:timer-engine` (покрытие 96% строк при пороге 85%, сценарии E-01…E-28 и
интегральный тест точности T-1), `:timer-service` (FGS `specialUse`,
partial WakeLock, уведомление с действиями, один exact-аларм как watchdog,
детект ограничений), персист сессии в `:core:datastore` и восстановление
после kill. Отличия реализации от тех-дизайна зафиксированы
в `docs/02-TIMER-CORE-DESIGN.md` §13.

Осталось единственное — **прогон матрицы устройств вживую** (M2): его нельзя
заменить автотестом, ради него фаза и стоит в плане первой. До прогона гипотеза
«FGS выживает на агрессивных OEM» остаётся недоказанной (риск R-1).

**Правка по итогам полевой проверки (2026-07-28).** Первый же запуск на
устройстве показал две ошибки проверочного экрана:

1. Все четыре ограничения показывались одним красным баннером «Оповещения могут
   запаздывать», хотя запаздывать от оптимизации батареи нечему: пока процесс
   жив, отсчёт идёт по монотонным меткам. Ограничения разделены по серьёзности
   (`RestrictionSeverity`): красным — только то, из-за чего занятие пройдёт
   молча или без управления (уведомления выключены, «Полная тишина»);
   энергосбережение и точные алармы стали **советом**, который закрывается
   навсегда и рядом даёт переход в нужный системный список — как и требовала
   политика `05-PLAY-DECLARATIONS.md` §5, не выполненная в коде Фазы 3.
2. Экран гас по системному таймауту: `FLAG_KEEP_SCREEN_ON` был отложен на
   Фазу 6, но без него проверочный экран невозможно наблюдать. Вынесен в
   `:core:designsystem` (`KeepScreenOn`) — Фаза 6 переиспользует.

Решения, принятые по ходу:

1. **Профиль сохраняется до перехода к этапу.** У несохранённого профиля нет
   идентификатора, а этап без владельца хранить негде. Поэтому «Добавить этап»
   и «Оповещения» сначала пишут профиль (валидируя имя) и только затем
   переходят — вместо второй, временной модели хранения ради одного перехода.
2. **Отмена удаления восстанавливает профиль новой строкой с прежним `uuid`.**
   `saveProfile` для существующего `id` делает `UPDATE`, который после удаления
   строки молча ничего не сделает. Настоящий идентификатор профиля — `uuid`
   (P1-7), номер строки деталь реализации.
3. **Перетаскивание дублировано стрелками «выше/ниже».** Перетащить строку
   невозможно ни в TalkBack, ни одной рукой на большом экране (критерий N-6).
4. **Предпрослушивание не вызывает `AlertPlayer.stop()`.** Проигрыватель общий
   с сервисом занятия: освобождение SoundPool из редактора оборвало бы сигналы
   идущего занятия.

Не закрыто автотестами и остаётся на Фазу 8: Compose UI-тесты критических
путей (5–7 сценариев по §4 тестовой стратегии) и живая проверка
перетаскивания на устройстве.

**Правка по итогам полевой проверки (2026-07-30).** Шесть замечаний с реального
занятия. Три из них — ошибки, три — недостающее поведение.

1. **Оповещения по умолчанию не сохранялись.** `saveProfile` пишет профиль
   целиком, а редактор профиля собирал `Profile` из одних лишь полей формы —
   и возвращал `defaultAlertConfig` (а заодно `iconId`, `totalDurationMode`,
   `fixedTotalSec`) к значениям по умолчанию. Теперь поля, которых на экране
   нет, помнятся моделью и перечитываются при возвращении с экрана оповещений.
   Регрессия закрыта тремя тестами `ProfileEditorViewModelTest`.
2. **Идущее занятие не было видно на главном экране.** Единственным следом
   занятия оставалось уведомление в шторке, а карточка профиля вела в редактор.
   Появилась полоса идущего занятия над списком (`ActiveSessionBar`): профиль,
   этап, остаток, пульсирующая точка на паузе — и переход к отсчёту по нажатию.
   Список читает состояние через узкий контракт `ActiveSessionSource`, а не
   через `SessionController` целиком.
3. **Тап по уведомлению открывал список профилей.** `ACTION_MAIN` с уже
   запущенной задачей просто поднимает её на передний план, не доставляя ни
   `onNewIntent`, ни экстр. Заменено ссылкой `yta://session/{profileId}`
   (`YtaDeepLinks` в `:core:common`), которую разбирает навигация: работает и
   для живой задачи, и для холодного старта.
4. **Запущенный профиль можно было редактировать.** Движок получает план при
   старте и второй раз его не собирает — правка под ногами у занятия не
   применилась бы, а удаление лишило бы сессию плана для восстановления.
   Запрет живёт в модели (`ProfilesViewModel.requestEdit`), а не в экране: свайп,
   меню и карточка ведут к одному действию. Карточка запущенного профиля вместо
   редактора открывает занятие.
5. **Свой звук этапа.** Возвращён из v1.1 (см. `06-MVP-SCOPE.md` §1.2):
   `AlertSound.CUSTOM` + `Alert.customSoundUri`, выбор через
   `ActivityResultContracts.OpenDocument` с разрешением, переживающим
   перезагрузку, воспроизведение — `CustomSoundChannel` на `MediaPlayer`.
6. **TTS выключен по умолчанию, добавлены ударения.** Синтезатор читает
   санскритские названия асан по своим правилам: «шавáсана» превращается в
   «шавасáну». Пресеты не переписывались — появился общий выключатель
   `AppSettings.voiceEnabled` (по умолчанию выключен) и поле «Произношение» у
   этапа (`Stage.voiceName`, миграция БД 1→2). Ударение вводится плюсом перед
   гласной и превращается в комбинирующий акут U+0301 — единственную пометку,
   которую понимают движки TTS (`Pronunciation`). Выключенный голос **не**
   деградирует на гонг: это решение пользователя, а не поломка движка.

Решения, принятые по ходу:

1. **Кнопки подписаны словами, а не значками.** «Пауза» читается с трёх метров
   однозначно, два вертикальных прямоугольника — нет. Побочная выгода: TalkBack
   получает имя действия без `contentDescription`. Заодно снят вопрос о значке
   паузы, которого нет в `material-icons-core`.
2. **Кегль таймера считается, а не подбирается измерением.** Шрифт
   моноширинный, ширина знака известна из кегля — значит, размер под доступную
   ширину вычисляется в одну формулу. Системный масштаб шрифта на цифры не
   действует: они и так занимают экран, а 200% превратили бы «12:34» в «12:».
3. **Ландшафт определяется по размеру окна, а не по ориентации устройства.**
   В многооконном режиме телефон стоит вертикально, а окно шире, чем выше.
4. **Системная «Назад» перехвачена во всех трёх режимах.** В обычном спрашивает
   подтверждение, в фокусе выходит из фокуса, под блокировкой игнорируется —
   иначе занятие обрывалось бы случайным свайпом от края экрана.

4. **«Этап 2/6 · осталось 45:45» в одну строку.** Строка занимала всю ширину

5. **Уведомления после занятия оставались в шторке.** Снимок FINISHED успевал

6. **Марки продукта не было видно нигде.** Верхняя панель списка профилей

   бы невозможное. Вместо него — баннер на рабочем экране с переходом в

4. **Онбординг просит только уведомления.** Отключение оптимизации батареи в

Панель занимает всю ширину и всю оставшуюся высоту — на телефоне 5" цифры выходят примерно в полтора раза крупнее. Значение по умолчанию прежнее — круг: настройка про читаемость, а выбирает её тот, кто на экран смотрит |
| 3 | Количество проведённых занятий в статистике не меняется | Не поломка, а молчащий порог D-S3: занятие короче минуты в журнал не попадает, а проверочный прогон со скипом этапов идёт секунд двадцать. Цепочка записи проверена целиком, включая новый инструментальный тест на живое обновление потоков Room (раньше все тесты журнала читали их через `first()` — то есть проверяли запрос, но не подписку). Экран итогов теперь называет причину: «Короче минуты — в журнал статистики не попало», порог у записи и у сообщения общий (`SessionLog.isRecordable`). Заодно исправлено глушение `CancellationException` в `runCatching` при записи журнала и поднят уровень лога до ошибки |

### Фаза 11 — Управление временем занятия · 6–8 дн

**Запрошена заказчиком 2026-08-04** пятым кругом полевой проверки. Шестнадцать
замечаний, из которых пять оказались одной задачей: у занятия не было конца,
заданного часами. Проектирование и решения —
[`docs/10-SESSION-TIME.md`](10-SESSION-TIME.md).

| # | Замечание | Решение |
|---|---|---|
| 1 | Свайп вниз в полноэкранном — пауза, выход — тап | Свайп ↓ в фокусе ставит на паузу вместо второго способа выйти; выход остался за тапом. Карта жестов обновлена (`docs/03-GESTURES.md` §3) |
| 2 | Справочник асан в поле названия этапа | `AsanaNameField` с фильтрацией по вводу; 90 названий в `res/values*/asanas.xml`, у каждого — форма произношения с ударением. Выбор заполняет и поле «Произношение». Поле осталось свободным: «Асаны стоя» справочником не ограничивается |
| 3 | Крупнее название следующего этапа и заметку | `YtaTextStyles.stageNext` 18 → 22 sp, заметка получила свой стиль `stageNote` (18 sp вместо `bodyMedium`), и заметка появилась в режиме фокуса, где её не было вовсе |
| 4 | Строка «Этап */* · Осталось» заметнее | Свой стиль `sessionMeta` (20 sp Medium вместо `bodyLarge` 16 sp) |
| 5 | Юзкейсы ±30 с, «Пред. этап», паузы | Разобраны в `docs/10-SESSION-TIME.md` §4. По ходу разбора нашлась ошибка: «Пред.» начинал этап заново даже тогда, когда его покинули досрочно, — то есть отмена промаха стирала пройденное. Теперь возврат на досрочно покинутый этап продолжает его с того же места и не объявляет заново |
| 6 | Два режима паузы | `PauseMode.SESSION` / `PauseMode.STAGE`: второй останавливает этап, но не часы занятия. Режим по умолчанию — в настройках, на занятии переключается нажатием по плашке паузы |
| 7 | Предлагать сохранить занятие с правками новым профилем | Экран итогов предлагает это, если правки были. В новый профиль уходят **эффективные** длительности, а не фактические: досрочный переход — событие дня, а ±30 с — осознанное решение |
| 8 | Целевое время занятия в редакторе профиля | Поля `targetDurationSec` / `targetToleranceSec` / `wrapUpOffsetSec`, миграция БД v3 → v4. Под списком этапов — «Распределено 64 из 60 мин · на 4 мин больше цели» |
| 9 | Переделать онбординг | Четыре слайда вместо трёх, каждый — обещание, а не описание кнопки. Четвёртый — про целевое время: новая главная возможность |
| 10 | Двусторонняя асана | Флаг `bilateral` у этапа; в плане разворачивается в две половины с подписями сторон. Длительность задаётся на одну сторону, правка ±30 с зеркалится на вторую |
| 11 | Отсечка «пора закругляться» | Разобрано в `docs/10-SESSION-TIME.md` §3: сигнал за N минут до цели, плашка «до конца 10:00, в плане 14:30» и кнопка «Ужать план» (`TimerCommand.FitToBudget`), которая пропорционально сжимает будущие этапы |
| 12 | «Осталось времени» независимо от переключений | Бюджет считается по часам занятия (`sessionElapsedMs`), а не по сумме этапов. Допуск профиля различает жёсткое и эластичное время — два сценария из замечания |
| 13 | Цифры по центру фигуры, плашка под ними | Слот поправки вычитается симметрично, а не снизу: цифры встали на ось фигуры, появление «+0:30» их по-прежнему не двигает |
| 14 | Обрезанная цифра в кружке дня календаря | Точка рядом с цифрой не помещалась в хорду круглой клетки. От четырёх занятий показывается одна цифра без точки, а клетка с занятиями получила заливку, растущую с их числом: форму месяца глаз берёт по пятнам |
| 15 | Логотип из `app/src/Yoga-Timing-Assistant.jpg` | `scripts/generate-logo.sh` собирает из одного исходника пять плотностей иконки, монохромный слой, знак интерфейса, картинку 512×512 для Play и цвет подложки. Векторные заглушки удалены |
| 16 | Статистика вываливается целиком | Разделы стали сворачиваемыми (`ExpandableSection`), заголовок в свёрнутом виде отвечает на главный вопрос раздела. По умолчанию раскрыт календарь; плитки сводки не сворачиваются никогда |

**DoD / M8 — «Время под контролем»:** занятие с целевым временем показывает

## 3. Модульная структура

```
:app                       — сборка, DI-граф, навигация, MainActivity
:core:designsystem         — тема M3, компоненты, типографика
:core:common               — утилиты, форматтеры времени, Result
:core:database             — Room, entities, DAO, миграции
:core:datastore            — настройки, персист сессии
:core:audio                — AlertPlayer, TTS, вибрация, audio focus
:domain                    — pure Kotlin: модели, use cases, правила наследования
:timer-engine              — pure Kotlin JVM: state machine, расчёт времени   ← ключевой
:timer-service             — Android-обвязка: FGS, WakeLock, notification, alarms
:feature:profiles          — список профилей
:feature:editor            — редакторы профиля / этапа / оповещений
:feature:timer             — рабочий экран
:feature:settings          — настройки, онбординг
:feature:stats             — статистика занятий (Фаза 10, docs/09-STATISTICS.md)
```

**Правило зависимостей:** `feature:*` → `domain` → ничего. `timer-engine` не зависит ни от чего, кроме stdlib + coroutines.

## 4. Тестовая стратегия

Отсутствует в ТЗ (пробел №1) — вводится здесь.

| Уровень | Что покрываем | Инструмент | Порог |
|---|---|---|---|
| Unit (JVM) | `timer-engine`: переходы, дрейф, ±30 с, FREE, edge cases | JUnit5 + `kotlinx-coroutines-test` (virtual time) | **≥ 85%** |
| Unit (JVM) | `domain`: наследование alert-конфигов, автораспределение FIXED, валидация | JUnit5 | ≥ 80% |
| Unit (JVM) | ViewModels | Turbine + fakes | ≥ 70% |
| Instrumented | Room DAO, каскады, миграции | AndroidJUnit4 + `MigrationTestHelper` | все DAO |
| Instrumented | Compose UI: критические пути (создать профиль → запустить → пройти) | Compose Test | 5–7 сценариев |
| Manual | Фоновая надёжность на матрице устройств | чек-лист `docs/04-DEVICE-MATRIX.md` | 100% перед каждым релизом |

**Особый тест (обязательный):** «Дрейф за сессию» — прогон виртуальных 90 минут с паузами, ±30 с, ручными переходами; накопленная ошибка < 1 с.

## 6. Рекомендации по scope MVP

Учитывая противоречие C-1 (макеты описывают больше, чем MVP), предлагаю зафиксировать:

**Входит в v1.0:**
- Профили + этапы, режим **SUM**
- Дублирование, избранное, поиск, категории
- Рабочий экран + режим фокуса + lock
- Фоновая работа, управление из шторки, восстановление сессии
- Оповещения: звук + вибрация + TTS, пресеты, наследование, тихие этапы
- Настройки, онбординг, RU/EN
- Демо-профили

- Режим FIXED + автораспределение *(экономия ~4 дн)*

**Экономия ~9 дней** при сохранении полной ценности для основного сценария US-1…US-4.

период (Фаза 10, `docs/09-STATISTICS.md`). Вынесена из v2.0 по запросу
