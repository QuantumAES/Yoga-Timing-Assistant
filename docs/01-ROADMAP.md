# Дорожная карта проекта «Yoga Timing Assistant»

**Дата:** 2026-07-26
**Базис:** `ТЗ.md` + `docs/00-ANALYSIS.md`
**Оценка:** 55–77 рабочих дней ≈ **11–15 недель** для 1 senior Android-разработчика
**Целевая дата MVP в Play (internal → production):** ~ноябрь 2026 при старте в августе

---

## 1. Стратегические принципы плана

### 1.1. Риск вперёд, красота потом

Главный риск проекта — **не вёрстка, а надёжность фонового исполнения** (R-1). Поэтому план намеренно нарушает привычный порядок «сначала UI, потом логика»:

> **Веха M2 (конец недели 4): вертикальный срез.**
> Захардкоженный профиль из 3 этапов честно отсчитывается на реальном устройстве при заблокированном экране, свёрнутом приложении и включённой оптимизации батареи. UI — три `Text` без стилей.

Если M2 не берётся на матрице устройств — весь проект пересматривается на неделе 4, а не на неделе 12. Это самая дешёвая точка для разворота.

### 1.2. Ядро таймера — чистый Kotlin без Android

`TimerEngine` выносится в отдельный JVM-модуль без единой ссылки на `android.*`. Следствия:
- тестируется виртуальным временем (`kotlinx-coroutines-test`) — 90-минутная сессия проверяется за миллисекунды;
- дрейф, границы этапов, ±30 с, переходы покрываются юнит-тестами, а не ручным сидением с секундомером;
- Android-специфика (WakeLock, Service, AlarmManager) — тонкий адаптер вокруг.

### 1.3. Порядок фаз соответствует убыванию риска

```
Риск ↓   Ядро таймера → Оповещения → Данные → Редакторы → Полировка
Стоимость исправления ↑
```

### Фаза 3 — Ядро таймера и фоновая работа · 8–12 дн ⚠️ КРИТИЧЕСКИЙ ПУТЬ

Самая рискованная и самая дорогая фаза. Не сокращать.

| Задача | Детали |
|---|---|
| `:timer-engine` (чистый JVM) | state machine IDLE→RUNNING→PAUSED→TRANSITION→FINISHED; отсчёт по `elapsedRealtime`; `next/prev/±30с`; FREE-этап (счёт вверх) |
| Юнит-тесты движка | виртуальное время: 90-мин сессия, дрейф, границы, все переходы, edge cases §8 ТЗ. **Покрытие ≥ 85%** |
| `TimerService` (FGS) | тип `specialUse` (P0-3), `START_STICKY`, partial WakeLock, notification с действиями Пауза/Далее/Стоп |
| Уведомление | обновление ≤ 1 Гц, корректная отмена, канал уведомлений |
| Watchdog-аларм | ровно один exact-аларм на ближайшее критичное событие (P0-2) |
| Персистентность сессии | по событиям, не по таймеру (P1-3); `bootId` + обе метки времени (P1-4) |
| Восстановление после kill | «Продолжить занятие?» если прошло < 5 мин |
| Детект ограничений | статус battery optimization / exact alarm / notifications → флаг для UI-баннера |
| Минимальный UI-заглушка | 3 `Text` + 3 кнопки, только для проверки |

**DoD / M2 — «Вертикальный срез»:**
- профиль из 3 этапов проходит целиком при заблокированном экране и свёрнутом приложении;
- управление из шторки работает;
- убийство процесса (`adb shell am kill`) → восстановление сессии;
- **проверено вручную на матрице устройств**, результат зафиксирован в `docs/04-DEVICE-MATRIX.md`;
- дрейф за 60 мин < 1 с (замер).

> Здесь принимается решение go/no-go по архитектуре. Если OEM-устройства не держат FGS — пересмотр (вплоть до отказа от полной фоновой работы в MVP и явного требования держать экран включённым).

**Состояние на 2026-07-28.** Код фазы готов и проверен автотестами:
`:timer-engine` (покрытие 96% строк при пороге 85%, сценарии E-01…E-28 и
интегральный тест точности T-1), `:timer-service` (FGS `specialUse`,
partial WakeLock, уведомление с действиями, один exact-аларм как watchdog,
детект ограничений), персист сессии в `:core:datastore` и восстановление
после kill. Отличия реализации от тех-дизайна зафиксированы
в `docs/02-TIMER-CORE-DESIGN.md` §13.

Осталось единственное — **прогон матрицы устройств вживую** (M2): его нельзя
заменить автотестом, ради него фаза и стоит в плане первой. До прогона гипотеза
«FGS выживает на агрессивных OEM» остаётся недоказанной (риск R-1).

## 3. Модульная структура

```
:app                       — сборка, DI-граф, навигация, MainActivity
:core:designsystem         — тема M3, компоненты, типографика
:core:common               — утилиты, форматтеры времени, Result
:core:database             — Room, entities, DAO, миграции
:core:datastore            — настройки, персист сессии
:core:audio                — AlertPlayer, TTS, вибрация, audio focus
:domain                    — pure Kotlin: модели, use cases, правила наследования
:timer-engine              — pure Kotlin JVM: state machine, расчёт времени   ← ключевой
:timer-service             — Android-обвязка: FGS, WakeLock, notification, alarms
:feature:profiles          — список профилей
:feature:editor            — редакторы профиля / этапа / оповещений
:feature:timer             — рабочий экран
:feature:settings          — настройки, онбординг
```

**Правило зависимостей:** `feature:*` → `domain` → ничего. `timer-engine` не зависит ни от чего, кроме stdlib + coroutines.

## 4. Тестовая стратегия

Отсутствует в ТЗ (пробел №1) — вводится здесь.

| Уровень | Что покрываем | Инструмент | Порог |
|---|---|---|---|
| Unit (JVM) | `timer-engine`: переходы, дрейф, ±30 с, FREE, edge cases | JUnit5 + `kotlinx-coroutines-test` (virtual time) | **≥ 85%** |
| Unit (JVM) | `domain`: наследование alert-конфигов, автораспределение FIXED, валидация | JUnit5 | ≥ 80% |
| Unit (JVM) | ViewModels | Turbine + fakes | ≥ 70% |
| Instrumented | Room DAO, каскады, миграции | AndroidJUnit4 + `MigrationTestHelper` | все DAO |
| Instrumented | Compose UI: критические пути (создать профиль → запустить → пройти) | Compose Test | 5–7 сценариев |
| Manual | Фоновая надёжность на матрице устройств | чек-лист `docs/04-DEVICE-MATRIX.md` | 100% перед каждым релизом |

**Особый тест (обязательный):** «Дрейф за сессию» — прогон виртуальных 90 минут с паузами, ±30 с, ручными переходами; накопленная ошибка < 1 с.

## 6. Рекомендации по scope MVP

Учитывая противоречие C-1 (макеты описывают больше, чем MVP), предлагаю зафиксировать:

**Входит в v1.0:**
- Профили + этапы, режим **SUM**
- Дублирование, избранное, поиск, категории
- Рабочий экран + режим фокуса + lock
- Фоновая работа, управление из шторки, восстановление сессии
- Оповещения: звук + вибрация + TTS, пресеты, наследование, тихие этапы
- Настройки, онбординг, RU/EN
- Демо-профили

**Переносится в v1.1:**
- Режим FIXED + автораспределение *(экономия ~4 дн)*
- Экспорт/импорт JSON *(экономия ~3 дн)*
- Кастомные звуки пользователя *(экономия ~2 дн)*
- FLASH-канал (экран/фонарик) *(экономия ~2 дн)*

**Экономия ~11 дней (≈2 недели)** при сохранении полной ценности для основного сценария US-1…US-4.

**v2.0** — по ТЗ §9 без изменений (облако, статистика, библиотека сценариев, Wear OS).
