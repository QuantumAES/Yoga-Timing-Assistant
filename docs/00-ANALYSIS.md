## 2. Блокеры (P0) — исправить до старта разработки

### P0-1. Файл ТЗ повреждён — утрачено ядро системы

Строка 1184:
```
    val resolvedAler< stages.lastIndex) {
```
Текст обрывается посреди определения `RuntimeStage` и склеивается с фрагментом `nextStage()`. Утрачены:
- окончание раздела 3.2 (модель `RuntimeStage`, `ResolvedAlert`),
- **раздел 3.3–3.4 — `TimerEngine`** (алгоритм отсчёта),
- **раздел 3.5 — `TimerService`** (жизненный цикл Foreground Service).

> Это ровно те два класса, вокруг которых строится весь проект. Раздел 3 нужно восстановить из исходника либо спроектировать заново (см. Roadmap, Фаза 0).

### P0-2. Механизм оповещений через AlarmManager упирается в квоту Doze

**ТЗ (§7.2):** «Оповещения планируются заранее через `setExactAndAllowWhileIdle` — гарантированное срабатывание даже в Doze».

**Реальность:** в Doze `*AndAllowWhileIdle`-алармы принудительно троттлятся системой — не чаще примерно **одного раза в 9 минут на приложение**. Дефолтная схема (§5.2) требует на каждый этап: старт, −2 мин, −1 мин, −10 сек, конец = **5 срабатываний внутри одного 10-минутного этапа**. Часть из них система молча отложит. Требование «± 1 сек» будет нарушено систематически.

**Решение (архитектурная замена):**
```
Primary:  единый цикл в Foreground Service + partial WakeLock.
          Планирование по абсолютным меткам elapsedRealtime,
          пробуждение через delay() до ближайшего события.
Watchdog: РОВНО ОДИН exact-аларм на ближайшее критичное событие
          (конец этапа), перевзводится после каждого срабатывания.
          Квота не расходуется, страховка от смерти процесса есть.
```
FGS + partial WakeLock — это тот же механизм, на котором работают секундомеры, трекеры пробежек и плееры. **Обязателен эмпирический тест на MIUI/OneUI/EMUI на вехе M2** — это главный технический риск проекта.

### P0-3. Foreground Service Type не объявлен (крах на Android 14+)

ТЗ не содержит ни слова о `foregroundServiceType`. С API 34 запуск FGS без объявленного типа и соответствующего разрешения → `MissingForegroundServiceTypeException`, приложение падает.

**Решение:** тип `specialUse`.
```xml
<uses-permission android:name="android.permission.FOREGROUND_SERVICE"/>
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_SPECIAL_USE"/>

<service android:name=".timer.TimerService"
         android:foregroundServiceType="specialUse"
         android:exported="false">
    <property android:name="android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE"
              android:value="class_timing_for_yoga_instructors"/>
</service>
```
Требует письменного обоснования в Play Console при публикации. Дополнительный плюс: `specialUse` не подпадает под введённый в Android 15 таймаут на длительные FGS (в отличие от `dataSync`).

### P0-4. Exact alarms — политика Google Play

`SCHEDULE_EXACT_ALARM` (API 31+) в Play ограничен. Приложения категории «будильник/таймер» имеют право на `USE_EXACT_ALARM` (выдаётся при установке, без диалога) — наш случай квалифицируется, **но требует декларации при публикации**, иначе отказ в ревью.

**Решение:** объявить `USE_EXACT_ALARM` (не `SCHEDULE_EXACT_ALARM`) + подготовить обоснование категории. Заложить в Roadmap (Фаза 9).

### P0-5. Неверный аудио-канал → сигналы будут не слышны

**ТЗ (§7 код `AlertPlayer`):** `USAGE_ASSISTANCE_SONIFICATION`.
Этот usage маппится на `STREAM_SYSTEM`: громкость привязана к системной, глушится в беззвучном режиме, не пробивает DND, у многих OEM выкручена в ноль. Для приложения, где инструктор кладёт телефон на коврик, — провал сценария.

**Решение:** `USAGE_ALARM` + `CONTENT_TYPE_SONIFICATION` (канал STREAM_ALARM: громкий, отдельный от медиа, переживает беззвучный режим и большинство конфигураций DND).

### P0-6. «Отдельный audio-stream» и «Игнорировать Не беспокоить» — невыполнимо как описано

- **§5.3 «Общая громкость сигналов, независимо от медиа, через отдельный audio-stream»** — Android не позволяет создать свой стрим. Доступен только выбор из системных usage.
  **Решение:** канал = STREAM_ALARM (уже независим от медиа), а ползунок «Громкость сигналов 0–100%» в приложении реализуется как **программный гейн** в `SoundPool.setVolume()` / `TextToSpeech` поверх системной громкости будильника. Формулировку в ТЗ переписать.

- **§5.3 / §Экран 6 «Игнорировать "Не беспокоить" [✓]»** — приложение не может односторонне обойти DND. Обход требует `ACCESS_NOTIFICATION_POLICY` (выдаётся в спец. настройках вручную) и влияет на каналы уведомлений, а не на произвольное аудио.
  **Решение:** переформулировать в «Использовать канал будильника (звучит в беззвучном режиме)» + опциональный deep-link в настройки DND. Обещание «приложение всё равно проиграет сигнал» из ТЗ убрать — оно не может быть выполнено гарантированно.

### P0-7. Каскады FK в схеме БД инвертированы + утечка сирот

```sql
-- profiles
default_alert_id INTEGER NOT NULL,
FOREIGN KEY (default_alert_id) REFERENCES alert_configs(id) ON DELETE CASCADE
```
Направление владения перевёрнуто: **удаление alert_config удалит профиль**. По смыслу профиль владеет конфигом, а не наоборот.

```sql
-- stages
FOREIGN KEY (alert_config_id) REFERENCES alert_configs(id) ON DELETE SET NULL
```
При удалении этапа его персональный `alert_config` и все его `alerts` **остаются в БД навсегда**. Механизма сборки мусора нет → неограниченный рост таблиц.

Плюс: `NOT NULL` FK на профиле создаёт циклическую зависимость при вставке (нужен конфиг до профиля, а конфиг логически принадлежит профилю) — решаемо транзакцией, но это лишняя сложность на ровном месте.

**Решение (см. §4) — денормализация.**

### P0-8. Запрос отключения оптимизации батареи в онбординге

**§Экран 7:** «предложение отключить оптимизацию батареи».
Прямой вызов `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` — рискованная зона политики Play (разрешено только когда основная функция без него невозможна; ревью трактует неоднозначно и часто отклоняет).

**Решение:** не запрашивать напрямую. Показывать deep-link на системный экран (`ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS`) **не в онбординге, а по факту** — при первом запуске занятия, вместе с объяснением. Ниже риск отказа + выше конверсия (пользователь уже понимает, зачем).

### P0-9. Критерий приёмки недостижим в текущей формулировке

**§10:** «При заблокированном экране и свёрнутом приложении **все** оповещения срабатывают вовремя (± 1 сек)».

Android не даёт такой гарантии ни одним API — OEM-надстройки (MIUI, EMUI, ColorOS) убивают процессы по собственным правилам независимо от FGS.

**Решение — переписать критерий:**
> На эталонной матрице устройств (Pixel, Samsung, Xiaomi), при выданном разрешении на уведомления и снятой оптимизации батареи: 100% оповещений в пределах ±1 с на 60-минутной сессии при заблокированном экране. Без снятой оптимизации батареи: не хуже ±3 с на Pixel/Samsung; для агрессивных OEM приложение обязано **обнаружить** факт ограничения и показать баннер.

### P0-10. Русский TTS может физически отсутствовать на устройстве

Голосовые оповещения — заявленная ключевая фича (US-4). Но русский голос не гарантирован: на устройствах без сервисов Google, на «чистых» прошивках, при удалённых языковых пакетах `TextToSpeech.isLanguageAvailable()` вернёт `LANG_MISSING_DATA`.

**Решение:** обязательная проверка на старте + деградация: (а) предложить установку языкового пакета, (б) fallback на звуковой канал, (в) не давать включить VOICE-канал в UI, если голос недоступен. Заложить в Фазу 4.

| # | Проблема | Решение |
|---|---|---|
| P1-1 | `AlarmScheduler.scheduled` — список в памяти. При смерти процесса алармы остаются висеть, `cancelAll()` их не найдёт | Хранить requestCodes в DataStore, либо отказаться от множественных алармов (см. P0-2) |

## 4. Ревизия модели данных

### Проблема
4 таблицы (`profiles`, `stages`, `alert_configs`, `alerts`) + 3 `@Relation`-обёртки + ручная транзакция `saveFullProfile()` + инвертированные каскады + утечка сирот.

При этом `alerts` **никогда не запрашиваются независимо** — они всегда читаются и пишутся целиком вместе с владельцем.

### Предложение: `AlertConfig` → JSON-колонка

```kotlin
@Serializable
data class AlertConfig(
    val presetType: AlertPreset = AlertPreset.STANDARD,
    val masterVolume: Int = 70,
    val alerts: List<Alert> = emptyList()
)

@Entity(tableName = "profiles")
data class ProfileEntity(
    @PrimaryKey(autoGenerate = true) val id: Long = 0,
    val uuid: String,
    val name: String,
    // ...
    @ColumnInfo(name = "default_alert_config") val defaultAlertConfig: AlertConfig,  // TypeConverter → JSON
)

@Entity(tableName = "stages", foreignKeys = [/* только profile_id CASCADE */])
data class StageEntity(
    // ...
    @ColumnInfo(name = "alert_config") val alertConfig: AlertConfig? = null,  // null = наследование
)
```

**Выигрыш:**
- 4 таблицы → **2**; каскады → один, тривиальный и корректный
- Сироты невозможны by design (P0-7 исчезает целиком)
- Циклическая зависимость при вставке исчезает
- `saveFullProfile()` из ручной 3-шаговой транзакции → обычный upsert
- `kotlinx.serialization` уже в стеке для экспорта → тот же формат переиспользуется в БД и в JSON-экспорте
- Миграции проще: изменение структуры Alert не требует SQL-миграции, только версионирование внутри JSON

**Цена:** нельзя сделать `SELECT ... WHERE alert.channelMask = ...`. Для этого домена такой запрос не нужен и в ТЗ не встречается.

> Рекомендую принять. Экономия — оценочно 3–4 дня разработки и весь класс багов с целостностью.

## 5. UX-замечания

### 5.1. Рабочий экран противоречит собственному принципу

§1 и §6.1 требуют «glanceable, считывается за 1–2 с с 2–3 метров, минимум вложенности». Макет Экрана 4 содержит **7 интерактивных контролов** (−30, ⏸, +30, Пред., След., 🔒, ✕) плюс 4 информационных блока. С 3 метров это нечитаемо, а на ходу — непопадаемо.

**Предложение — иерархия по частоте использования:**
```
Постоянно:  гигантский таймер (тап → фокус)
Часто:      ⏸ Пауза (главная кнопка, ≥72dp) │ След. ›
Редко:      −30/+30, ‹ Пред.  → второй ряд, меньше, или long-press
Единично:   🔒 Lock, ✕ Стоп   → верхний бар
```

### 5.2. Конфликт жестов

ТЗ одновременно требует: «тап по таймеру → режим фокуса» (§Экран 4), «свайп для управления» (§4.3), «разблокировка двойным тапом» (§6.3), «свайп по карточке влево — удаление» (§Экран 1) и drag-and-drop в списке этапов (§Экран 2).

**Нужна единая карта жестов.** Черновик:

| Жест | Обычный режим | Режим фокуса | Lock |
|---|---|---|---|
| Тап по таймеру | → фокус | → выход из фокуса | игнор + подсказка |
| Свайп ← / → | нет | пред./след. этап | игнор |
| Long-press таймер | нет | нет | → разблокировка (1 с, с прогресс-индикатором) |

Двойной тап для разблокировки — **слишком слабая защита**: телефон на коврике, рядом занимающиеся. Заменить на long-press 1 с.

### 5.3. Неопределённое поведение (требует решения)

| Ситуация | В ТЗ | Нужно определить |
|---|---|---|
| «Свободный» этап (FREE) и общий прогресс | не описано | Как считать «Осталось всего X мин», если этап бессрочный? Предлагаю: исключать FREE из total, показывать «≥ 42 мин» |
| ±30 сек в режиме FIXED | «корректно пересчитывают общий тайминг» (§10) — правило не задано | Три варианта: (а) общее время растёт, (б) компенсация за счёт последнего этапа, (в) компенсация пропорционально остатку. Предлагаю (а) + визуальный индикатор расхождения |
| Профиль без этапов | не описано | Запретить запуск, дизейблить кнопку ▶ |
| Этап 0 сек | валидация «> 0» есть, но не для FREE | ОК, но нужен и верхний предел (напр. 4 ч) |
| Входящий звонок | «оповещения в очередь / пропускаются» — «/» не разрешено | Решить однозначно. Предлагаю: START/END — отложить до возврата фокуса (≤10 с), WARNING — пропустить |
| Отсчёт «за 10 сек» | голосом? | Голосовой отсчёт 10..1 конфликтует с очередью TTS и с «тихой шавасаной». Предлагаю: только тики звуком, для REST-этапов принудительно выключен |

### 5.4. Прочее

- **Динамические цвета (Material You)** на рабочем экране опасны: сгенерированная из обоев палитра может дать низкий контраст. Рабочий экран должен использовать **фиксированную high-contrast палитру**, игнорируя dynamic color. Остальные экраны — можно.
- **Time-picker ч:м:с** для длительности этапа избыточен (часы почти всегда 0). Лучше: минуты+секунды + чипы быстрого выбора `5 / 10 / 15 / 20 / 30 мин`.
- **Онбординг 4 слайда** до первой ценности — высокий отвал. Предлагаю 2 слайда + запрос разрешений по факту необходимости (см. P0-8).
- **Landscape** для рабочего экрана заявлен, но макета нет. Нужен отдельный layout (таймер слева, управление справа), а не автоповорот portrait-вёрстки.
- **TalkBack «на неигровых экранах»** — формулировка бессмысленна для этого приложения. Заменить на явный список: список профилей, редакторы, настройки — полная поддержка; рабочий экран — озвучивание состояния и действий.

## 6. Пробелы в ТЗ (не покрыто вообще)

1. **Тестовая стратегия** — для приложения, чья главная ценность в точности, отсутствует полностью. Критично.
2. **Матрица устройств** для приёмки фоновой работы.
3. **CI/CD**, подпись релиза, управление keystore.
4. **Крашлитика/аналитика** — offline-first декларирован, но без crash reporting отладка фоновых падений невозможна. Нужно решение (Firebase Crashlytics vs полный отказ) с учётом §8 «Приватность».
5. **Монетизация** — не указана вообще. Влияет на архитектуру (billing-модуль, feature-gating).
6. **Аудио-ассеты**: количество, формат, длительность, источник, лицензии.
7. **Политика конфиденциальности** — обязательна для публикации в Play даже при полностью локальных данных.
8. **Минификация R8 / размер APK / App Bundle**.
9. **Поведение при обновлении приложения** с активной сессией.
10. **Wear OS в v1.1** — заявлен одной строкой; по факту это отдельный проект (~3–4 недели).
