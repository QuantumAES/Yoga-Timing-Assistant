# Зафиксированный scope MVP v1.0 и критерии приёмки

**Статус:** ✅ утверждено 2026-07-26
**Основание:** решение заказчика по вопросам §9 `00-ANALYSIS.md` — «урезанный MVP, оба архитектурных исправления приняты, ядро проектируем заново»

Этот документ **имеет приоритет над `ТЗ.md`** в случае расхождений. Макеты в ТЗ описывают целевой продукт (v1.1), а не v1.0.

---

## 1. Состав v1.0

### 1.1. Входит

| Блок | Объём |
|---|---|
| Профили | CRUD, дублирование, избранное, поиск, фильтр по категориям, цвет/иконка |
| Режим общего времени | **только SUM** (общее время = сумма этапов) |
| Этапы | CRUD, drag-and-drop сортировка, типы NORMAL / TRANSITION / REST / FREE, цвет, заметка инструктору |
| Рабочий экран | таймер, прогресс-кольцо, общий прогресс, следующий этап, заметка, управление, режим фокуса, lock |
| Фоновая работа | Foreground Service, работа при заблокированном экране, управление из шторки, восстановление после kill |
| Оповещения | каналы SOUND / VOICE (TTS) / VIBRATION; триггеры START / WARNING(×N) / END; наследование Profile→Stage; пресеты Стандарт/Тихий/Только вибро/Максимум |
| Настройки | громкость сигналов, ducking, TTS (язык/скорость/тест), тема, динамические цвета, wake lock, автозатемнение |
| Онбординг | 2–3 слайда + разрешения |
| Локализация | RU / EN |
| Демо-данные | «Хатха 60 мин», «Инь-йога 90 мин», «Медитация 20 мин» |

### 1.2. Перенесено в v1.1

| Фича | Причина | Экономия |
|---|---|---|
| Режим FIXED + автораспределение | Не нужен для US-1…US-5; требует отдельной модели пересчёта при ±30 с | ~4 дн |
| Экспорт / импорт JSON | Инфраструктура (uuid, стратегия конфликтов, SAF) при нулевом спросе на старте | ~3 дн |
| Загрузка пользовательских звуков | SAF + копирование + управление хранилищем + права на URI | ~2 дн |
| Канал FLASH (экран / фонарик) | Конфликтует с автозатемнением, требует отдельной проработки | ~2 дн |

**Итого экономия ≈ 11 рабочих дней (~2 недели).**

> Схема БД проектируется **сразу с учётом v1.1**: поля `uuid`, `total_duration_mode`, `fixed_total_sec` создаются в версии 1, чтобы не потребовалась миграция. UI для них просто не строится.

### 1.3. v2.0 — без изменений

Облачная синхронизация, библиотека готовых сценариев, статистика занятий, фоновая музыка, Wear OS.

## 2. Разрешение противоречий ТЗ

| ID | Противоречие | Решение |
|---|---|---|
| **C-1** | §9 обещает SUM-only, макеты описывают FIXED + экспорт | Приоритет за §9. Макеты Экрана 2 в части FIXED и Экрана 6 в части «Данные» — это v1.1 |
| **C-2** | «AlarmManager (exact) **/** собственный service-loop» — выбор не сделан | Решено в **ADR-001**: FGS-цикл как основной механизм, один exact-аларм как watchdog |
| **C-3** | minSdk 26 vs требования API 31/34 | Три ветки по версиям, описаны в `05-PLAY-DECLARATIONS.md` §3. `compileSdk = 37`, `targetSdk = 36`, `minSdk = 26` (уточнено в Фазе 1, см. ниже) |

> **Уточнение по SDK (Фаза 1, 2026-07-27).** `compileSdk` поднят с 36 до 37: актуальные
> AndroidX (`core-ktx 1.19`, `lifecycle 2.11`, `activity 1.13`) отказываются собираться
> против API 36. `targetSdk` при этом остаётся 36 — в новое рантайм-поведение Android 17
> не опрокидываемся, пока не пройдена матрица устройств. Поднятие `targetSdk` —
> осознанное решение Фазы 8–9 вместе с перепроверкой фоновой работы.
> Lint-проверка `OldTargetApi` отключена в конвенции сборки именно по этой причине.
| **C-4** | «Тёмная тема по умолчанию» vs выбор темы + динамические цвета | Приоритет: явный выбор пользователя → системная тема → тёмная. Динамические цвета применяются везде, **кроме рабочего экрана** (см. §4) |
| **C-5** | «Пропустить этап / Растянуть текущий» есть в §4.3, нет в макете | Не входит в v1.0. «Пропустить» покрывается кнопкой «След.», «Растянуть» — кнопкой +30 с |
| **C-6** | «Тихая шавасана» — особый триггер (§5.2) или автопресет по типу этапа (§Экран 3)? | **Автопресет на этапе редактирования.** При выборе типа REST редактор предлагает пресет «Тихий»; пользователь может отклонить. Демо-профили сидируются с уже применённым пресетом. Runtime-подмены каналов **нет** — она непредсказуема для пользователя и неотлаживаема |

## 3. Доопределённое поведение

Пункты, не описанные в ТЗ, но блокирующие реализацию.

| # | Ситуация | Правило v1.0 |
|---|---|---|
| B-1 | ±30 с в режиме SUM | Меняется длительность текущего этапа → общее время занятия растёт/сокращается на ту же величину. Правка накапливается (`adjustmentMs`) и отображается на рабочем экране |
| B-2 | ±30 с уводит остаток в ноль или минус | Этап немедленно завершается, END-оповещение проигрывается, переход к следующему |
| B-3 | Границы длительности этапа | 5 с … 4 ч. Эффективная длительность после правок клампится в те же границы |
| B-4 | FREE-этап и «Осталось всего» | FREE исключается из подсчёта остатка; UI показывает **«≥ 42 мин»** вместо «42 мин». Флаг `totalRemainingIsLowerBound` в снапшоте |
| B-5 | FREE-этап: оповещения | START отрабатывает. WARNING/END привязаны к концу этапа, которого нет → пропускаются. END проигрывается в момент ручного перехода |
| B-6 | Профиль без этапов | Запуск запрещён, кнопка ▶ задизейблена, в редакторе — подсказка |
| B-7 | WARNING с offset ≥ длительности этапа | Пропускается молча (например, «за 2 мин» на 90-секундном этапе). В редакторе — предупреждение при сохранении |
| B-8 | Входящий звонок | Потеря audio focus: START/END-оповещения **откладываются** до возврата фокуса, но не более чем на 10 с; WARNING-оповещения **пропускаются**. Таймер продолжает идти |
| B-9 | Оповещение «за 10 сек» | Только звуковые тики, без TTS-отсчёта (конфликтует с очередью TTS). Для этапов типа REST принудительно выключено |
| B-10 | Prev() — возврат к предыдущему этапу | START-оповещение нового (предыдущего) этапа отрабатывает; END-оповещение покидаемого этапа **не** проигрывается |
| B-11 | Перезагрузка устройства во время сессии | Сессия не восстанавливается (согласно ТЗ §8). При следующем запуске — уведомление «Занятие было прервано перезагрузкой» |
| B-12 | Восстановление после kill процесса | Предложение «Продолжить занятие?» если с момента сохранения прошло < 5 мин |
| B-13 | Обновление приложения во время сессии | Процесс убивается системой → тот же путь, что B-12 |
| B-14 | Смена системного времени во время сессии | Не влияет: отсчёт ведётся по `elapsedRealtime()`, а не по стенным часам |
| B-15 | Состояние TRANSITION из ТЗ §3.1 | **Убрано из движка.** Переход — визуальный эффект UI, отсчёт не останавливается (иначе каждая анимация крадёт время). См. `02-TIMER-CORE-DESIGN.md` §2 |

## 4. Правило по динамическим цветам

| Экран | Dynamic color |
|---|---|
| Список профилей, редакторы, настройки, онбординг | ✅ применяется (если включено в настройках) |
| **Рабочий экран занятия** | ❌ **не применяется никогда** |

**Обоснование:** палитра Material You генерируется из обоев пользователя и не гарантирует контраст. Рабочий экран обязан читаться с 2–3 метров в приглушённом свете — это требование §1 и §6.1 ТЗ. Он использует фиксированную high-contrast палитру с проверенным коэффициентом контраста ≥ 7:1 (AAA).

> **Уточнение (2026-07-29).** Фиксированная палитра рабочего экрана — не значит
> «всегда тёмная». Изначально вариант был один, тёмный: экран проектировался под
> зал с приглушённым светом. На устройстве выяснилось, что светлый список
> профилей и чёрный таймер следом за ним читаются как две разные программы.
> Поэтому у `TimerPalette` два варианта, светлый и тёмный, и выбирает между ними
> тема приложения (`LocalYtaDarkTheme`). Требование не ослаблено: оба варианта
> проверены на контраст ≥ 7:1, динамические цвета сюда по-прежнему не попадают
> ни при каких настройках. Инструктор, ведущий занятие в тёмном зале, выбирает
> тёмную тему явно — и получает ровно ту палитру, что была.

## 5. Критерии приёмки v1.0 (переписаны)

Заменяют §10 ТЗ. Формулировки приведены к проверяемому виду; недостижимые гарантии убраны (см. P0-9).

### 5.1. Функциональные

| # | Критерий | Метод проверки |
|---|---|---|
| A-1 | Профиль на 60 мин из 6 этапов создаётся через UI, сохраняется и воспроизводится с корректными переходами | Ручной сценарий + Compose UI-тест |
| A-2 | Из шторки уведомления доступны и работают Пауза / Далее / Стоп | Ручной сценарий на каждом устройстве матрицы |
| A-3 | Этап типа REST с пресетом «Тихий» не проигрывает звуковых сигналов ни на одном триггере | Ручная проверка + unit-тест резолвера оповещений |
| A-4 | ±30 с изменяют длительность текущего этапа и общее время занятия согласно B-1; при уходе остатка в ноль — немедленный переход (B-2) | Unit-тест движка |
| A-5 | Дублирование профиля создаёт независимую копию, включая все этапы и конфиги оповещений | Instrumented-тест DAO |
| A-6 | При отсутствии русского TTS-голоса приложение не падает, показывает предупреждение и деградирует на звуковой канал | Ручная проверка на устройстве с удалённым языковым пакетом |
| A-7 | Профиль без этапов невозможно запустить (B-6) | Compose UI-тест |

### 5.2. Надёжность таймера

| # | Критерий | Условия | Порог |
|---|---|---|---|
| **T-1** | Дрейф отображаемого времени за 90-минутную сессию с 5 паузами, 4 правками ±30 с и 2 ручными переходами | Виртуальное время, unit-тест | **< 1 с** |
| **T-2** | Все оповещения 60-минутной сессии срабатывают вовремя при заблокированном экране и свёрнутом приложении | **Эталонные условия:** Pixel / Samsung, оптимизация батареи снята, разрешения выданы | **100% в пределах ±1 с** |
| **T-3** | То же на устройствах с включённой оптимизацией батареи | Pixel / Samsung | **не хуже ±3 с**, потерь нет |
| **T-4** | То же на агрессивных OEM (Xiaomi/MIUI) | оптимизация включена | Допускается деградация, но приложение **обязано обнаружить** факт ограничения и показать баннер пользователю |
| **T-5** | Убийство процесса (`adb shell am kill`) во время сессии | любое устройство | Сессия восстанавливается с корректным остатком, отклонение < 2 с |
| **T-6** | Перезагрузка устройства во время сессии | любое устройство | Сессия не восстанавливается, показано уведомление (B-11), приложение не падает |

> **T-4 — не отказ, а требование наблюдаемости.** Мы не можем победить MIUI, но обязаны честно сообщить пользователю, что сигналы могут запаздывать, и объяснить, как это починить.

### 5.3. Нефункциональные

| # | Критерий | Порог |
|---|---|---|
| N-1 | Холодный старт до интерактивного списка профилей | < 2 с (Pixel 6a или эквивалент) |
| N-2 | Отклик UI на действия рабочего экрана | < 100 мс |
| N-3 | Расход батареи за 90-минутную сессию при выключенном экране | < 5% на эталонном устройстве |
| N-4 | Покрытие тестами модуля `:timer-engine` | ≥ 85% строк |
| N-5 | Читаемость таймера | распознавание цифр с 3 м при яркости 30% — ручная проверка |
| N-6 | Доступность | TalkBack проходит все экраны; шрифт 200% не ломает вёрстку; контраст рабочего экрана ≥ 7:1 |
| N-7 | Полный офлайн | все сценарии работают в авиарежиме |
| N-8 | Размер релизного App Bundle | < 15 МБ |

## 6. Что считается Definition of Done для v1.0

1. Все критерии §5 выполнены и зафиксированы протоколом.
2. Матрица устройств (`04-DEVICE-MATRIX.md`) пройдена полностью.
3. CI зелёный: build + unit + instrumented + lint + detekt.
4. Декларации Play подготовлены (`05-PLAY-DECLARATIONS.md`), политика конфиденциальности опубликована.
5. Лицензии на все аудио-ассеты сохранены в репозитории.
6. Проведён внутренний прогон реального 60-минутного занятия на реальном коврике с реальным телефоном.

> Пункт 6 не формальность. Ни один автотест не поймает «сигнал звучит слишком резко для шавасаны» или «с коврика не видно цифры».
